# Документация по мерам безопасности — OrgMFA (система многоступенчатой аутентификации)

**Версия:** 1.0 · **Дата:** 01.11.2026 · **Объект:** учебный стенд ВКР «Authenticator» (FastAPI, Python 3.12)

Документ описывает **все меры безопасности, фактически реализованные в коде проекта**, с указанием
места реализации (файл/функция), назначения меры и ссылки на признанный стандарт/рекомендацию.
В конце приведены известные ограничения стенда и рекомендации по доработке перед промышленной эксплуатацией.

---

## 1. Обзор архитектуры защиты

Система реализует многофакторную аутентификацию как конечный автомат стадий сеанса
(`password → mfa | step_up | setup → authed`) с оценкой риска входа, защитой от перебора,
replay-атак и перехвата сеанса, шифрованием секретов второго фактора и полным журналом
событий безопасности.

| Модуль | Ответственность за безопасность |
|---|---|
| `app/security.py` | Криптографическое ядро: Argon2id, TOTP, AES-256-GCM, резервные коды |
| `app/risk.py` | Risk-based MFA: скоринг, lockout, rate limiting, replay-детектор, step-up |
| `app/store.py` | Хранилище: сессии state-machine, одноразовые токены сброса, audit log |
| `app/main.py` | Протокол аутентификации, cookie-сессии, сервисный контракт ИС |
| `app/mailer.py` | Защищённая доставка уведомлений (STARTTLS / implicit TLS) |
| `tests/test_mfa.py` | Верификация мер безопасности автотестами (40 тестов) |

## 2. Защита паролей (`app/security.py`, `app/store.py`)

### 2.1 Хэширование Argon2id
- **Мера:** пароли хранятся только в виде хэша Argon2id; параметры: `memory_cost=65536 KiB (64 MiB)`, `time_cost=3`, `parallelism=4`, `hash_len=32`, `type=Argon2Type.ID` (`_hasher = PasswordHasher(...)`).
- **Назначение:** стойкость к перебору и GPU/ASIC-атакам (memory-hard); Argon2id — победитель PHC и рекомендован OWASP.
- **Соответствует:** RFC 9106, OWASP ASVS v4.1 §A2 / V2.4, NIST SP 800-63B §5.1.1.2.
- Соль генерируется автоматически внутри хэша; открытый текст пароля нигде не сохраняется и не логируется.

### 2.2 Прозрачная миграция («rehash-on-login»)
- **Мера:** `verify_password()` возвращает флаг `needs_rehash`; при входе устаревший хэш пересчитывается с актуальными параметрами (`main.py: login()`, блок «успешная 1-я ступень»).
- **Назначение:** инкрементальное усиление стойкости без смены паролей пользователями.

### 2.3 Политика сложности пароля
- **Мера:** `check_password_policy()`: минимальная длина 10 символов, обязательны верхний+нижний регистр и цифра, запрет совпадения с логином, чёрный список распространённых паролей.
- Применяется при регистрации (`store.create_user`) и при смене пароля по ссылке восстановления (`/reset-password`).
- **Соответствует:** NIST SP 800-63B §5.1.1.2.

### 2.4 Выравнивание времени ответа (anti user-enumeration)
- **Мера:** при неизвестном логине выполняется фиктивная хэш-проверка `await _dummy_hash(password)` — время ответа неотличимо от случая «неверный пароль».
- Сообщения об ошибке одинаковы для «нет такого логина» и «неверный пароль» («Неверный логин или пароль», `_login_error()`).
- Аналогично устроена регистрация: занятая почта даёт нейтральное сообщение без раскрытия деталей (`user.register_failed`, reason в аудит).
- **Соответствует:** OWASP ASVS V2.3.1, NIST SP 800-63B §3.1.1.2 (provisional message).

## 3. Второй фактор — TOTP (`app/security.py`)

- **Генерация seed:** `generate_totp_secret()` — 20 байт (160 бит) из CSPRNG `secrets.token_bytes`. Требование RFC 6238 (≥128 бит) превышено.
- **Параметры кода:** 6 цифр, период 30 с, допуск окна ±1 шаг (`TOTP_DIGITS/TOTP_PERIOD/TOTP_WINDOW`) — защита от рассинхронизации часов и сетевых задержек без чрезмерного расширения окна.
- **Проверка:** `verify_totp()` сначала валидирует формат (только цифры, ровно 6 символов) — мусорные/словарные попытки отклоняются до криптографической проверки.
- **Provisioning:** `otpauth://` URI + QR-код PNG (`qr_png_data_uri`, byte mode, ERROR_CORRECT_M) — секрет передаётся устройству пользователя только через камеру, без ручного ввода в основном потоке привязки и без логов.
- **Соответствует:** RFC 6238 / RFC 4226, OWASP ASVS V2.6.3 (OTP-факторы).

### 3.1 Шифрование секретов TOTP при хранении
- **Мера:** seed никогда не хранится в открытом виде — `encrypt_secret()` шифрует его **AES-256-GCM** (аутентифицированное шифрование: конфиденциальность + целостность).
  - nonce 12 байт — свежий криптослучайный на каждое шифрование (`secrets.token_bytes(12)`), повтор nonce исключён;
  - формат хранения: `base64url(nonce ‖ ciphertext ‖ tag)`;
  - ключ KDF: `hashlib.scrypt(MFA_MASTER_KEY, salt="mfa-kdf-salt", n=2^14, r=8, p=1, dklen=32)` — производный от master-key из переменной окружения.
- **Master key** задаётся через env `MFA_MASTER_KEY` (генерация `secrets.token_hex(32)` — 256 бит); в `.env.example` это явно предписано; файл `.env` исключён из git.
- **Соответствует:** NIST SP 800-38E (GCM), OWASP ASVS V6.2 (криптография), V6.4 (защита ключей).

### 3.2 Резервные коды (потеря второго фактора)
- **Генерация:** `generate_recovery_codes()` — 10 кодов по 10 символов из алфавита без неоднозначных знаков (исключены O/0, I/1/l), ~40+ бит энтропии на код, CSPRNG `secrets.choice`. Соответствует минимуму NIST SP 800-63B §5.1.1.1 (≥20 бит) с запасом.
- **Хранение:** только SHA-256 хэш кода (`hash_recovery_code()`), plaintext нигде не сохраняется; коды показываются пользователю **ровно один раз** при привязке/перевыпуске.
- **Одноразовость:** использованный хэш удаляется из набора сразу после принятия (`u.recovery_hashes.remove(h)` в `/verify-recovery` и `/api/auth/recovery`).
- **Защита от timing-атак:** сравнение хэшей через `constant_time_eq()` (`hmac.compare_digest`).
- **Нормализация ввода** (`normalize_recovery_code`) — регистро- и пробело-независимый ввод без снижения энтропии (usability по NIST §5.2).

## 4. Управление сеансами (`app/main.py`, `app/store.py`)

### 4.1 Cookie-сессии
- **Мера:** токен сессии доставляется только в cookie `mfa_session` с атрибутами `HttpOnly`, `SameSite=Lax`, `max_age=8 ч`, `path=/` (`_set_cookie`).
  - HttpOnly — cookie недоступна скриптам (снижение последствий XSS);
  - SameSite=Lax — межсайтовые POST не получают cookie (частичная CSRF-защита).
- **Энтропия токена:** `uuid4().hex ×2` = 256 бит (`store.create_session`).
- **State machine стадий:** промежуточные стадии (`mfa`, `step_up`, `setup`) имеют короткий TTL (60–120 с / 10 мин); полная авторизация выдаётся только после прохождения всех требуемых ступеней. Доступ к личному кабинету и API возможен только со стадии `authed` (кроме ограниченного `setup`-режима привязки фактора).
- **Истечение и очистка:** просроченные сессии отвергаются при каждом чтении (`get_session`) и физически удаляются при создании новой сессии.
- **Выход:** `/logout` и `/api/auth/logout` удаляют сессию из БД, гасят step-up-флаги и сбрасывают cookie (server-side invalidation, а не только удаление cookie на клиенте).

### 4.2 Принудительная MFA и защита перевыпуска фактора
- **Мера:** без привязанного TOTP полный доступ запрещён — пользователь попадает во временную `setup`-сессию (TTL 10 мин) только для привязки фактора (событие `auth.setup.required`).
- **Перевыпуск фактора из авторизованной сессии требует повторного ввода пароля** (`/enroll/totp`: `password_confirmation_failed` → 403). Украденная cookie не позволяет молча подменить второй фактор.
- При перевыпуске старые резервные коды **аннулируются**, новые показываются один раз.
- Показ Base32-секрета вручную (`/enroll/totp/secret`) доступен только владельцу активной `setup`-сессии и фиксируется в аудите (`enroll.totp.secret_shown`).
- Привязка завершается только после подтверждения TOTP-кодом (`/enroll/totp/confirm`) — `mfa_enabled` не включается автоматически.

### 4.3 Сброс сеансов при смене пароля
- **Мера:** после успешной смены пароля все активные сессии пользователя удаляются (`store.drop_user_sessions`), lockout снимается, счётчик неудач обнуляется.

## 5. Восстановление пароля (`app/main.py`, `app/store.py`)

- **Анти-оракул:** ответ формы `/forgot-password` идентичен для существующего и несуществующего адреса — адрес электронной почты не раскрывается (NIST SP 800-63B §3.2.1).
- **Токены:** cryptographically secure `secrets.token_urlsafe(32)` (256 бит), **TTL 15 минут** (`RESET_TTL_SEC`), **одноразовые**: в БД хранится только `sha256(токен)` (`token_hash`), plaintext токена не сохраняется — дамп SQLite не даёт активных ссылок.
- **Гашение до валидации:** токен потребляется (`consume_reset_token`) *до* проверки сложности нового пароля — «зомби-токенов» с повторным использованием нет.
- GET-открытие страницы использует non-consuming проверку `peek_reset_token` (токен не тратится на показ формы).
- Письмо содержит инструкцию «если вы не запрашивали сброс — смените пароль и проверьте журнал».
- Все события (`auth.reset_requested`, `auth.password_reset_ok`, `auth.reset_requested_unknown`) пишутся в аудит.

## 6. Защита от перебора и атак на учётные данные (`app/risk.py`)

| Мера | Реализация | Параметры | Стандарт |
|---|---|---|---|
| Rate limiting по IP | скользящее окно `_hits` / `rate_limited()`, HTTP 429 | 10 попыток / 60 с | OWASP ASVS V2.2.1 |
| Lockout учётной записи | `apply_failed_attempt()`, `is_locked()`, HTTP 403 | 5 неудач → блокировка 15 мин | NIST SP 800-63B §3.2.2 |
| Уведомление владельца | фоновое письмо при достижении порога (`NOTIFY_FAILED_AT=5`) и при блокировке | — | ASVS V2.2.1 |
| Счётчики по всем ступеням | неудачная проверка TOTP также увеличивает `failed_attempts` и ведёт к lockout | — | ASVS V2.2.1 |
| Раздельные события неуспеха | unknown user / locked / bad password / bad TOTP / bad recovery — отдельные записи аудита | — | ASVS V7 |

## 7. Risk-based (адаптивная) аутентификация (`app/risk.py`)

Каждый вход получает score по независимым признакам (функция `score_login`):

| Признак риска | Вес | Детектируемая угроза |
|---|---|---|
| Серия неудачных попыток (≥3) | +15/попытка, до 60 | brute-force / credential stuffing |
| Новый device/User-Agent | +15 | вход с чужого устройства |
| Смена User-Agent | +10 | подмена клиента |
| Вход вне доверенной подсети (не 127./10./192.168./::1) | +10 | атака извне периметра |
| Вход вне рабочих часов (8:00–19:00) | +8 | нетипичное поведение |
| Реактивация «спящей» учётки (>30 дней) | +8 | компрометация давно не используемой записи |

Пороги вердиктов (`decision()`): `allow < 55 ≤ step_up < 85 ≤ block`.

- **Step-up реально ужесточает вход:** при вердикте `step_up`/`block` создаётся сессия со стадией `step_up` и сокращённым TTL (60 с), и вход завершается **только после подтверждения третьим фактором** (один резервный код дополнительно к TOTP). Реализовано симметрично в браузерном (`/verify-totp`, `/verify-recovery`) и API-потоках.
- **Anti-loop:** флаги пройденных ступеней хранятся на сессию (`mark_totp_step_done` / `mark_recovery_step_done`); каждый фактор засчитывается ровно один раз, порядок произвольный, повторный расход резервных кодов в одной сессии исключён (тест `test_step_up_exhausted_recovery_codes`).
- **Калибровка против ложных срабатываний:** одиночный «бытовой» признак не ужесточает вход (`STEP_UP_MIN_FACTORS=2`, `require_step_up`) — штатный вход сотрудника всегда `allow`.
- Риск-скор сохраняется в сессии (`risk_score`) и отдаётся ИС при интроспекции; риск оценивается **до** сброса счётчика неудач (иначе перебор не влиял бы на вердикт).

## 8. Защита от replay-атак (`app/risk.py`)

- **Мера:** детектор повторного использования одноразового кода — словарь `(user_id, code) → срок годности` (`remember_code`/`code_already_used`, окно 90 с ≈ TOTP-окно + запас). Принятый код запоминается и **не принимается повторно**, даже в пределах допустимого временного окна.
- Факт попытки replay фиксируется в аудите (`auth.fail.replay`; в деталях — только последние 2 символа кода, без раскрытия кода целиком).
- Резервные коды одноразовы по построению (удаление хэша после использования).
- **Соответствует:** OWASP ASVS V3.2 / NIST SP 800-63B §4.1.5 (verifier replay resistance).

## 9. Безопасность интеграционного контракта ИС (`app/main.py`)

- Эндпоинты `/api/auth/*`, `/api/introspect`, `/api/auth/logout` закрыты **сервисным ключом `X-Service-Key`** (`_check_service_key`).
- Сравнение ключа — `constant_time_eq` (`hmac.compare_digest`) → защита от timing-атак на заголовок.
- Если ключ не настроен (`MFA_INTEGRATION_KEY` пуст) — API полностью закрыт (fail-closed, 403), попытки логируются (`integration.denied`).
- Интроспекция (`/api/introspect`, аналог RFC 7662) сообщает субъекта, пройденные факторы, риск-скор и активна ли сессия; logout немедленно делает интроспекцию `active:false` (тест `test_api_logout_revokes_introspection`).
- **Ограничение стенда (задокументировано):** вместо mTLS/OIDC используется статический ключ; для продакшена заявлена замена на mTLS/OIDC.
- Rate limiting и lockout действуют и в API-потоке (`/api/auth/login` возвращает 429/403), т.е. интеграционный контракт защищён от перебора не слабее браузерного входа.

## 10. Журналирование событий безопасности (audit log, `app/store.py`)

- **Append-only журнал** `audit_log` (SQLite): время, событие, субъект, IP, успех/неуспех, структурированные детали (JSON).
- Регистрируются все значимые события: `auth.risk_score`, `auth.success(_recovery)`, `auth.fail.*` (unknown_user/password/locked/totp/recovery/replay), `auth.rate_limit`, `auth.step_up.*`, `auth.setup.required`, `auth.reset_requested(_unknown)`, `auth.password_reset_ok`, `enroll.totp.started/confirmed/denied/secret_shown`, `recovery.regenerated`, `session.logout`, `integration.auth.*`, `integration.denied`, `mail.sent/failed/console`, `user.created/registered_ok/failed`.
- **Приватность деталей:** в журнал не пишутся секреты — для replay-события сохраняется только суффикс кода (`code_suffix`); пароли, TOTP, резервные коды и plaintext-токены в аудит не попадают никогда.
- Журнал доступен пользователю в личном кабинете (последние 15 событий) — поддержка самодиагностики при компрометации.
- **Соответствует:** OWASP ASVS V7.1–V7.4.

## 11. Безопасная передача писем (`app/mailer.py`)

- SMTP только через **STARTTLS (порт 587)** или **implicit TLS SMTP_SSL (порт 465)** с `ssl.create_default_context()` — проверка сертификата и hostname по умолчанию.
- Учётные данные — **App Password Gmail**, берутся исключительно из переменных окружения; `.env` не коммитится (см. п. 13).
- Без настройки SMTP включается режим «console»: письма не уходят в сеть, факт фиксируется в аудите — безопасный default для тестов/стенда.
- Ошибки доставки не роняют аутентификацию (экстренный catch всех исключений); отправка — фоновая задача (BackgroundTasks), не удлиняющая ответ входа.
- Шаблоны писем содержат рекомендации действий при незапрошенном сбросе/атаке.

## 12. Защита шаблонов и ввода (Web layer)

- Все пользовательские данные выводятся через **Jinja2 Templates с автоэкранированием** (autoescape по умолчанию для `.html`) — защита от отражённого XSS в страницах входа/кабинета/журнала.
- Server-side валидация всех форм: длина/регистр/цифры пароля, формат e-mail (`valid_email`, ограничение длины 254), формат TOTP (только цифры, 6 символов), нормализация e-mail/login (`strip().lower()`).
- User-Agent truncaturится до 200 символов перед сохранением; JSON-парсеры API защищены try/except от malformed input.
- CORS не включён (same-origin приложение); CSRF компенсируется комбинацией `SameSite=Lax` + server-side state machine стадий + требованием пароля для чувствительных операций (перевыпуск фактора/кодов).
- SQL-запросы — **только параметризованные** (`?`-плейсхолдеры), конкатенация пользовательского ввода в SQL отсутствует — защита от SQL-инъекций.
- **Соответствует:** OWASP ASVS V5.

## 13. Управление секретами и конфигурацией

- Секреты только через переменные окружения: `MFA_MASTER_KEY`, `SMTP_USER/PASS`, `MFA_INTEGRATION_KEY`, `MFA_BASE_URL` (см. `.env.example`).
- `.env` не попадает в git; в репозитории — только шаблон с плейсхолдерами и инструкцией по App Password и генерации 256-битного master key.
- Fail-closed поведение при отсутствии ключей: интеграционный API закрыт; для мастер-ключа задокументирована обязательность замены dev-значения вне стенда.
- Зависимости зафиксированы минимально и современно (`argon2-cffi`, `cryptography` ≥42, `pyotp`, `qrcode`); небезопасных примитивов для секретов нет (для необратимых хэшей — SHA-256, для паролей — Argon2id, для кодов — `hmac.compare_digest`).

## 14. Верификация мер безопасности автотестами (`tests/test_mfa.py`, 40 тестов)

| Группа | Что подтверждается |
|---|---|
| Crypto unit | Argon2id verify/rehash, политика паролей, TOTP round-trip и истечение окна, AES-GCM шифрование секретов, необратимость хэшей резервных кодов, валидность QR otpauth |
| Risk engine | скоринг и вердикты, «штатный вход не step-up», одиночный бытовой признак не ужесточает, два независимых — ужесточают, серия перебора — step-up, trusted-подсети, replay-детектор, rate limit, lockout после 5 неудач |
| Browser flow | полный двухфакторный поток, неверный пароль не создаёт сессию, MFA обязательна даже при верном пароле, setup-сессия и QR-привязка, replay одного TOTP заблокирован, lockout при брутфорсе, вход резервным кодом, инвалидация сессии logout'ом, запись аудита, резервные коды выдаются один раз, перевыпуск фактора требует пароль |
| Step-up | обычный вход без step-up, TOTP→резервный и резервный→TOTP, исчерпание кодов не даёт войти |
| Integration API | отказ без X-Service-Key, полный granted-поток, неверный пароль + lockout, расход ОДНОГО кода при step-up, риск «спящей» учётки, отзыв интроспекции после logout |

Запуск: `pytest` (настройки в `pytest.ini`).

## 16. Известные ограничения учебного стенда (осознанные, задокументированы в коде)

1. **Cookie `secure=False`** — запуск по HTTP на localhost; перед эксплуатацией включить HTTPS и `secure=True` (комментарий в `_set_cookie`).
2. **CSRF-токены не реализованы** — частично компенсировано `SameSite=Lax`; для продакшена добавить per-session CSRF tokens.
3. **Dev fallback мастер-ключа** (`"dev-master-key-change-me"` при пустом `MFA_MASTER_KEY`) — в промышленной версии обязателен KMS/HSM или env-секрет (комментарий в `_aes_key`).
4. **In-memory состояние risk-движка** (replay-детектор, rate limiter, step-up-флаги) — рассчитано на однопроцессный uvicorn; при масштабировании вынести в Redis/БД (указано в `risk.py`).
5. **Сервисный ключ X-Service-Key** вместо mTLS/OIDC для интеграции с ИС.
6. **SQLite вместо PostgreSQL** — интерфейс репозитория изолирован в `store.py` для бесшовной замены.
7. **Демо-пользователь `ivanov` с известным паролем** создаётся на startup — удалить перед реальной эксплуатацией (блок `startup()` в `main.py`).
8. **Служебный заголовок `X-Force-Step-Up`** для демонстрации step-up на защите ВКР — удалить/запретить политикой в промышленной версии (комментарий в `_force_step_up`).
9. Строгая DNS/MX-валидация e-mail не выполняется (декларировано в docstring `valid_email`).
